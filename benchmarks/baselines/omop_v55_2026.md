# OMOP v5.5 Mapping — Pipeline Timings (v0.0.19 release)

Environment: WSL2, DuckDB 1.5.x, Python 3.10, fhir4ds 0.0.19 (in-memory).
Source: the library demo bundle (10 resources: 2 patients + spine +
monolithic ConceptMap), replicated with distinct ids/references.

| Scale | Resources staged | Composition (13 VDs -> omop.*) | Query all 8 tables | Total rows |
|---|---|---|---|---|
| 1x demo | 10 | 438 ms | 113 ms | 10 |
| 50x demo | 500 | 448 ms | 166 ms | 145,050 |
| 200x demo | 2,000 | 452 ms | 658 ms | 8,320,200 |

- VD generation (parse + SQL emit, all 13 views): **214 ms** — one-time,
  independent of data volume.
- Composition cost is dominated by the 13 view CREATEs (plan-time), not
  data: 438→452 ms from 10 to 2,000 resources.
- Row multiplication: the 200x run yields 8.3M rows (the join against
  the flattened ConceptMap fans each event coding across map rows in the
  view; consumers filter/aggregate downstream).

Cross-reference: real-Athena CONCEPT-table numbers (5.7M concepts,
mapping throughput) come from the medterm4ds side — this benchmark uses
the demo ConceptMap; the join shape is identical, only map cardinality
differs.

Regression: viewdef/CQL/FHIRPath/DQM suites are gated by the master
conformance run (2869/2869 at this release).
