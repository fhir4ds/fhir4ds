# Benchmark Baselines

This directory contains checked-in performance baselines used by report-only
benchmark comparison tooling.

## DQM 2025 Baseline

`dqm_2025.json` is the baseline for the QI-Core 2025 DQM conformance timing
suite. It has the same structure as `conformance/reports/dqm_report.json`,
generated by:

```bash
python3 conformance/scripts/run_dqm.py
```

The DQM performance workflow compares the current report to this baseline with:

```bash
python3 benchmarks/runner/dqm_perf_report.py \
  --current conformance/reports/dqm_report.json \
  --baseline benchmarks/baselines/dqm_2025.json \
  --output-json benchmarks/output/dqm-performance-report.json \
  --output-md benchmarks/output/dqm-performance-report.md
```

## When to Update

Update the baseline when a performance change is intentional and reviewed, for
example:

- A translator optimization improves one or more measures.
- A correctness change necessarily increases SQL generation or execution time.
- The benchmark fixture suite changes.
- The CI runner environment changes enough that old timings are no longer
  comparable.

Do not update the baseline just to hide an unexplained regression.

## Update Procedure

### Recommended Helper

Use the helper script when possible:

```bash
python3 benchmarks/runner/update_dqm_baseline.py --run
```

This runs DQM conformance, verifies that all expected measures passed, updates
`benchmarks/baselines/dqm_2025.json`, and regenerates the comparison report
against the previous checked-in baseline.

To validate an existing report without writing the baseline:

```bash
python3 benchmarks/runner/update_dqm_baseline.py --dry-run
```

### Manual Procedure

1. Run the DQM conformance suite locally:

   ```bash
   python3 conformance/scripts/run_dqm.py
   ```

2. Confirm the run is still fully conformant:

   ```text
   Summary: 47/47 measures passed (100.0%)
   ```

3. Review the generated timings in `conformance/reports/dqm_report.json`.

4. Generate and review the comparison report before replacing the baseline:

   ```bash
   python3 benchmarks/runner/dqm_perf_report.py \
     --current conformance/reports/dqm_report.json \
     --baseline benchmarks/baselines/dqm_2025.json \
     --output-json benchmarks/output/dqm-performance-report.json \
     --output-md benchmarks/output/dqm-performance-report.md
   ```

5. Copy the reviewed report into the baseline, or run the helper without
   `--dry-run`:

   ```bash
   cp conformance/reports/dqm_report.json benchmarks/baselines/dqm_2025.json
   ```

6. Commit the baseline with a message that explains why the performance
   expectation changed.

## Thresholds

The report flags a measure only when both thresholds are exceeded:

- Current metric is at least `2.0x` the baseline.
- Current metric increased by at least `500 ms`.

The default workflow is non-blocking. Use `--fail-on-regression` only after the
baseline and hosted runner variability are stable enough for a hard gate.

## Baseline refresh (2026-11-23, v0.0.26)

`baselines/dqm_2025.json` was refreshed from the v0.0.26 release tree (dev @
`f53ba6a5fcc`), DECLARED native 1.5.6 engine (`allow_unsigned_extensions` +
`fhir4ds.register()` — banner `fhirpath_cpp/cql_cpp: true`), 47/47 measures at
100% accuracy, suite total 79.0 s.

vs the previous baseline (v0.0.18, 2026-10-24, 85.0 s) the suite got FASTER
overall (0.93x), but two measures grew through intentional correctness-surface
changes to the generated SQL (same class as the 0.0.8 Domain 7 refresh):

- **CMS0334**: 14.5 s -> 21.9 s total; SQL 226 KB -> 767 KB; `sql_execution_ms`
  2.6 s -> 15.1 s (5.8x, the only tool-flagged metric). Cause: the 0.0.20-0.0.26
  correctness campaigns changed the SQL shape — strict-profile `meta.profile`
  membership conjuncts (v0.0.25 campaign), negation-profile alternate-URL
  exclusion, sub-day `during` precision UDF routing (QA-D4H-001), offset-bearing
  interval parameter bounds (QA-D4E-001), and count-union star rewrites
  (QA-D3E-001/QA-D4S-001). Translation and SQL generation both got FASTER
  (0.62x / 0.54x) over the same period. Accuracy unchanged at 100%.
- **CMS1218**: 3.9 s -> 5.6 s total (`sql_execution_ms` 0.5 s -> 1.9 s, flagged);
  same correctness-surface class.

The drift record (current-vs-v0.0.18-baseline comparison) was preserved at
`benchmarks/output/dqm-performance-report-vs-v0018-baseline.{json,md}` before
the refresh (gitignored; regenerate by comparing against git history).

## OMOP v5.5 mapping timings

`omop_v55_synthea_2026.json` / `.md` — the real-data baseline (25-patient
Synthea cohort + 71,444-concept chunked RxNorm ConceptMap from the
`fhir4ds/omop-demo` HF dataset): staging 12 ms–2.4 s, composition ~450 ms
flat, 1,488 drug rows; browser run ~29 s in DuckDB-WASM.

## OMOP v5.5 demo-bundle timings
