A clinical quality measure is a good stress test for a query engine. You take an
HL7 CQL library — hundreds of definitions, value sets, temporal intervals,
polymorphic FHIR fields — compile it to one population query, and run it over an
entire patient cohort at once. Nothing is cached between measures, and nothing is
pre-flattened: the engine reads raw FHIR JSON.

We wanted a number for "how does this behave as the cohort grows", and more
importantly *where the time goes*. So we built a ladder — the same measures at
100, 1,000 and 5,000 patients — with a query profile captured at every rung.

The first profile pointed at something specific. We fixed it. Then we re-ran the
entire ladder, and the profile pointed at something *else*. This post is the
diagnosis, the fix, the re-measurement — and the lesson that the first fix moves
the bottleneck rather than removing it.

## Method, and one thing we deliberately did not count

The headline metric is **execution time only**. CQL parsing, library translation,
population-SQL generation and result conversion are measured and reported — but
separately, as compile diagnostics. They never enter a speedup or a
milliseconds-per-patient figure. Those phases are one-time per library version;
a production deployment pays them at deploy, not at query.

- **Engine:** FHIR4DS compiles each measure's CQL into a single population SQL
  query over an in-memory DuckDB table of FHIR resources. Every number below was
  run identically on **both DuckDB 1.5.6 and 2.0.0**.
- **Timing:** median of three executions of the *same pre-compiled* SQL.
  DuckDB re-plans on every execution, so planning is inside the number;
  compilation is not.
- **Cohorts:** nested deterministic prefixes of one Synthea generation (100 /
  1,000 / 5,000 patients, 6.3 million resources at the top rung), measurement
  period 2026 calendar year, one fresh process per rung, corpus loaded from disk
  once per rung.
- **Measures:** five, spanning the complexity range — **CMS68** (documentation
  of current medications), **CMS22** (BP screening follow-up), **CMS2**
  (depression screening, the largest generated SQL), **CMS130** (colorectal
  cancer screening), **CMS133** (cataracts, ~110 distinct Condition value-set
  retrieves).
- **Baseline:** the clinical-reasoning engine (Java, HAPI-based) evaluated per
  patient, **linearly extrapolated** from its per-patient cost. We did not run it
  at these sizes. That matters, and it is the first caveat below.

## What the first profile found: the corpus read 42 times

When we first built this ladder (October 2026), the profile had one dominant
fact. The corpus held 6.3 million rows, and CMS130's query read **263 million**
of them:

| Measure | Scans | Rows scanned | Amplification | Scan share of time |
|---|---|---|---|---|
| CMS68 | 7 | 43.9M | 7.0x | 63.8% |
| CMS130 | 42 | 263.5M | 42.0x | 99.5% |
| CMS2 | 18 | 112.9M | 18.0x | 86.1% |

The ratio was **rung-invariant** — 41.5x at 100 patients, 42.0x at 5,000, with
an identical scan count. That is the cleanest statement of the model: cost was
`O(scan sites × corpus)` with a fixed multiplier. Every retrieve CTE re-read the
whole `resources` table, so a measure with 42 retrieves read the corpus 42 times,
at every scale.

Static analysis of the SQL could rank the measures but badly understated the
gap — a structural score (scan sites, `SELECT DISTINCT`, `json_extract`, date
casts, joins, derived tables) gave CMS130 2.7x CMS2's score while it measured
17.5x CMS2's cost. The missing term is *how many rows each predicate runs over*,
and per-row predicate cost, which only a profile shows.

Two intuitive hypotheses the profile killed, worth recording because both were
wrong:

**"The value-set and interval calls are the expensive part."** CMS2 contained
far more value-set membership, coding-match and interval calls than CMS130. It
was also three times cheaper per resource. The calls are not the cost — *where
they run* is.

**"Deduplicating the full JSON payload is a major win."** Every retrieve CTE
deduplicates on the whole JSON payload; that dedup accounted for 0.2–13% of
operator time. Real, but nowhere near the top of the list.

## What we shipped

Three changes, each aimed at a profile finding:

1. **Materialized per-resource-type base scans.** Retrieves of one resource type
   now share a materialized CTE (`_rt_Observation`, `_rt_Encounter`, …) and each
   value-set retrieve filters that materialization instead of re-reading the
   table. Where the profile saw 42 independent scans, CMS130's SQL now has a
   handful of base scans feeding 34 value-set CTEs.
2. **Retrieve CTEs deduplicated by identity.** Retrieves with the same
   (resource type, value set, profile) key share one CTE instead of being
   re-emitted.
3. **The `_patients` CTE rewritten.** It used to enumerate `patient_ref` over
   every resource row with two correlated subqueries per row — 27% of CMS68's
   operator time. It is now a single scan of the Patient rows.

## The re-measured ladder

Same corpus, same cohorts, same measures, current engine (DuckDB 1.5.6):

| Measure | 100 | 1,000 | 5,000 | vs October |
|---|---|---|---|---|
| CMS68 | 54 ms | 115 ms | 474 ms | **11.0x** |
| CMS130 | 2,132 ms | 13,106 ms | 58,289 ms | **4.4x** |
| CMS2 | 1,908 ms | 2,141 ms | 3,450 ms | **4.2x** |

Against the extrapolated Java baseline at 5,000 patients that is roughly 600x
(CMS130), 170x (CMS2) and — for CMS68, which is down to 0.09 ms per patient —
beyond a number worth quoting.

Memory moved as much as time. The first 5,000-patient rung needed a 48 GB
memory limit to avoid spilling and peaked at 43.9 GB of RSS. The same rung on
the current engine peaks at **17.4 GB** — materializing small per-type CTEs is
far cheaper than re-scanning (and re-filtering) the corpus per retrieve.

And the population counts are byte-identical to the October run — the speedups
changed no answers.

## The profile now points somewhere else

Here is the part we find most instructive. After the fix, re-profiling the
5,000-patient rung:

| Measure | Scan share (Oct) | Expression-eval share (now) |
|---|---|---|
| CMS68 | 63.8% | 10.9% (scans still lead) |
| CMS130 | 99.5% | **99.6%** |
| CMS2 | 86.1% | **81.5%** |
| CMS133 | — | 3.7% (96.2% scans) |

The amplification is gone — rows scanned dropped 4–10x per measure — but on the
predicate-heavy measures the *dominant cost is now expression evaluation*: the
`fhirpath` / value-set / interval predicates that DuckDB pushes into scan
filters, evaluated over every row of a type partition before selectivity. In one
CMS68 operator, a filter costing 3x its own scan emits **zero rows**.

That is the next target (precomputing the derived temporal bounds the predicates
recompute per row), and it is the point of the whole exercise: **profile, fix,
profile again.** The first fix did not remove the bottleneck; it moved it. If we
had stopped at the wall-clock improvement we would have shipped the engine
believing scans were still the story.

## Two engines, one SQL

Because both DuckDB lines ship the same generated SQL, the rerun also gives a
clean engine comparison at 5,000 patients:

| Measure | 1.5.6 | 2.0.0 | Delta |
|---|---|---|---|
| CMS68 | 474 ms | 225 ms | −52.5% |
| CMS130 | 58,289 ms | 5,458 ms | **−90.6%** |
| CMS133 | 44,991 ms | 5,064 ms | **−88.7%** |
| CMS22 | 4,722 ms | 5,869 ms | +24.3% |
| CMS2 | 3,450 ms | 39,134 ms | **+1,034%** |

DuckDB 2.0.0 is dramatically faster on the scan-heavy measures — the ones the
October diagnosis was about — but regresses CMS2 badly. CMS2's generated SQL is
1.5 MB of a single query with thousands of pushed-down predicates, and the 2.0
planner handles that shape worse, not better. Until that is understood,
per-measure engine choice is a deployment decision, which is only possible
because both engines run the same SQL.

## Read these numbers with four caveats

We would rather publish the caveats than have someone discover them.

1. **The Java baseline is extrapolated, not measured.** It is the reference
   engine's per-patient cost multiplied by cohort size. Per-patient evaluation
   does scale roughly linearly, but this is an extrapolation and is labelled as
   one in the source data.
2. **Population counts in this benchmark are raw per-definition truth values**,
   with no CQM attribution masking applied. On synthetic data the numerator can
   exceed the denominator. They are sanity signals that the query ran, not
   reported measure rates — accuracy is validated separately against the official
   HL7 test bundles (47/47 QI-Core 2025 and 73/73 US-Core 2025). CMS133 has
   empty populations on this cohort (Synthea generates no cataracts-surgery
   patients) while still executing its full 110-retrieve query — it measures
   machinery cost, not clinical yield.
3. **Operator shares under parallelism are not wall-clock seconds.** Per-operator
   timings are summed across worker threads; the shares show relative cost
   distribution. Wall time is the measured execution figure.
4. **The before/after comparison is one machine, one corpus.** Absolute numbers
   will differ elsewhere; the amplification ratios and the attribution shift are
   the transferable findings.

The full report — every rung, every operator bucket, both engines, the
structural scoring method and the compile diagnostics — is in
[`benchmarks/scaling/SCALING.md`](https://github.com/fhir4ds/fhir4ds/blob/dev/benchmarks/scaling/SCALING.md)
in the repository, regenerated by `benchmarks/scaling/make_report.py` from the
raw run data.

The short version for anyone building on a SQL-native clinical engine: the
standards are not what makes a measure expensive. Access patterns are. A measure
that reads its corpus 42 times costs 42 corpora' worth of time no matter how
elegant the CQL is — and you will only find that out by profiling the operators,
not by reading the SQL. Then, once you have fixed it, profile again: the first
fix moves the bottleneck, it does not remove it.
