To make this highly performant, you cannot treat FHIRPath as a simple regex or JSONPath replacement. You must architect it to leverage DuckDB's vectorized engine while respecting FHIR's unique semantics.

1. The Fundamental Architectural Shift
The core difference is that JSONPath is a selection language for trees, while FHIRPath is a functional language for collections. In FHIRPath, even a single value is a Collection<T> of size 1.

Vectorized Execution Model
Instead of evaluating row-by-row (slow), your extension should implement a vectorized operator. DuckDB processes data in "Vectors" (usually 2,048 rows).

The Problem: FHIRPath collections can have variable lengths per row (e.g., Row 1 has 3 names, Row 2 has 0). This breaks fixed-width vector alignment.

The Solution: Use List Vectors. Your extension should map FHIRPath operations to DuckDB’s internal LIST type operations, where each "slot" in the vector is a pointer to a flattened array of values for that row.

2. Handling FHIRPath-Specific Logic
You should implement a specialized FHIRPath Compiler within the extension that translates expressions into a Physical Plan of DuckDB functions.

A. Graph Traversal vs. Field Access
In JSONPath, $.name is a key lookup. In FHIRPath, Patient.name implies a type-check (is this a Patient?) followed by a collection projection.

Optimization: Use DuckDB’s Struct/Map types for input. If the input is a Parquet file with a known schema (like those generated by Pathling or Bunsen), your extension should bypass the JSON parser entirely and perform direct columnar offsets.

B. "Hidden" Semantics (Polymorphism)
FHIR uses choice[x] types (e.g., valueQuantity or valueCodeableConcept).

Implementation: Map these to DuckDB UNION types. Your FHIRPath evaluator should handle the "polymorphic resolution" at the metadata level so the execution engine only scans the specific branch of the union required by the expression.

C. The "Empty Collection" Logic
In FHIRPath, {} + 5 is {} (empty), whereas in many SQL engines, NULL + 5 is NULL.

Architecture: You must ensure your internal operators handle the "Empty set propagation" correctly without falling back to standard SQL NULL logic, which can lead to incorrect FHIR validation results.

3. High-Performance Execution Strategy
The "JIT-Lite" Compilation
For complex paths like Patient.item.where(code = '123').value, don't interpret the string for every row.

Parse once into an Abstract Syntax Tree (AST).

Bind the AST to the table schema to resolve types.

Generate a function chain using DuckDB’s C++ API that operates on DataChunk objects.

Indexing and Filter Pushdown
Since FHIRPath is often used for filtering (where()), your extension should implement TableFunction support that allows DuckDB’s optimizer to push filters down into the scan.

Example: If a FHIRPath expression is Patient.active = true, the extension should signal to DuckDB that it can use the Parquet statistics (min/max) for the active column to skip row groups.

4. Proposed Implementation Stack
Language: C++11 (Standard for DuckDB extensions).

Parser: Use a generated ANTLR or PEG parser for the FHIRPath R4/R5 grammar.

Internal Representation: | FHIRPath Concept | DuckDB Equivalent |
| :--- | :--- |

| .where() / .exists() | Vectorized Selection Vector |

1. High-Performance Integration Pattern
You should avoid calling fhirpathpy.evaluate() on every single row inside a standard loop. Instead, use DuckDB's PyArrow integration to process rows in batches.

import duckdb
import pyarrow as pa
import fhirpathpy
from functools import lru_cache

# 1. Pre-compile paths to avoid parsing overhead for every batch
@lru_cache(maxsize=128)
def get_compiled_path(path_string):
    return fhirpathpy.compile(path_string)

# 2. Define the vectorized logic
def fhirpath_vec(json_column: pa.Array, path_string: str) -> pa.ListArray:
    # Compile once per query using the cache
    compiled = get_compiled_path(path_string)
    
    results = []
    # Convert the batch to Python dictionaries for fhirpath-py
    # Note: .to_pylist() is the bottleneck; for extreme perf, 
    # use a library that navigates Arrow buffers directly.
    data = json_column.to_pylist() 
    
    for resource in data:
        if resource is None:
            results.append(None)
        else:
            # fhirpath-py returns a list; DuckDB expects a list for LIST type
            results.append(compiled(resource))
            
    return pa.array(results, type=pa.list_(pa.string()))

# 3. Register as a Vectorized UDF
con = duckdb.connect()
con.create_function(
    "fhirpath", 
    fhirpath_vec, 
    [pa.string(), pa.string()], 
    pa.list_(pa.string()), 
    type='arrow'
)

How to fix it:
